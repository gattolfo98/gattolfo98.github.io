If you've ever needed to call a native library from Java, you had only one option; JNI (Java Native Interface). You write your Java class, annotate a method with `native`, fire up `javah` (or `javac -h`), implement a C function with a signature that looks like it was generated by a drunk donkey, compile a shared library, load it at runtime, and pray that nothing segfaults.

Until **Project Panama** appeared in the JDK. Introduced as a set of JEPs under the OpenJDK umbrella, it ships two major APIs: the **Foreign Function & Memory API** (FFM) [JEP-424](https://openjdk.org/jeps/424) and the **Vector API** [JEP-426](https://openjdk.org/jeps/426). This series focuses on the FFM API, how it works, what problems it solves, and where it falls short.

## Why JNI Is Fundamentally Broken

JNI's problems aren't just ergonomic, they're architectural.

Every native call via JNI requires a C stub. The stub receives a `JNIEnv*` pointer and a `jobject` (or `jclass` for static methods), and from there you manually unpack arguments, pin arrays, call the actual native function, and convert return values back. The compiler helps you with none of this. If you mess up the type mapping. Say, you pass a `jint` where the native function expects a `long`, you get undefined behavior, not a compile error.

```c
JNIEXPORT jlong JNICALL Java_com_example_Foo_nativeSum
  (JNIEnv *env, jobject obj, jlong a, jlong b) {
    return a + b;
}
```

This is a basic example, there is no real situation where we write a function that simple, in a real Real-world usage we probably have a library with dozens of struct, unions, function pointers, and platform-specific types. The glue code becomes larger than the actual logic, and it's entirely untestable at the Java layer.

JNI is not a suitable option to use if you want to call a native library from Java in a reliable way.

Project Panama throws out this model entirely (luckily). Let's see what it replaces it with.


## What Project Panama Sets Out to Fix
Panama doesn't patch JNI, it replaces it for the common case. The FFM API (finalized in Java 22 as [JEP 454](https://openjdk.org/jeps/454)) provides:

- **`MemorySegment`**: a safe, bounded, lifetime-scoped abstraction over a region of memory, whether heap, off-heap, or mapped.
- **`Arena`**: controls the lifetime of native memory. When an Arena closes, all segments allocated through it are freed. This is RAII for Java.
- **`MethodHandle`-based native calls**: no C stubs, no `javah`, no shared library glue. You describe the native function's signature in Java and call it directly.
- **`jextract`**: a tool that reads C headers and generates Java bindings automatically.

## First program with Panama

First of all, if you want to test out the features of Project Panama you need Java, to be more specific a fairly recent version (at least JDK 22), in my case I will use Java 26 (only because I like using the latest version available). 

In my case the set-up was easy, I'm using Intellij IDE, so I just had to create a Java project (gradle or maven, is not important) and remember to set the JDK version to 26.

Then, let's start with something simple:

```java
public static void main(String[] args) throws  Throwable{
    Linker nativeLinker = Linker.nativeLinker();
    SymbolLookup stdLibLookup = nativeLinker.defaultLookup();

    MethodHandle strlen = nativeLinker.downcallHandle(
        stdLibLookup.find("strlen").orElseThrow(),
            FunctionDescriptor.of(JAVA_LONG, ADDRESS)
    );


    try (Arena arena = Arena.ofConfined()){
        MemorySegment cString = arena.allocateFrom("Hello, Panama!");

        long length = (long) strlen.invokeExact(cString);

        System.out.println("The length of the C string is: "+ length);
    }
}
```

As usual, everything starts from main, and for convenience I will keep all the code there.

First of all, we create a `Linker` object calling `Linker.nativeLinker()`, that provides access to foreign functions from Java code, and access to Java code from foreign functions.

Then we need a `SymbolLookup`, we can get one from the `Linker` using the `defaultLookup()` method, A symbol lookup retrieves the address of a symbol in one or more libraries. A symbol is a named entity, such as a function or a global variable.

Now we can retrieve the function that we are interested in calling, to have a directly executable reference to it we use the `downcallHandle(...)` method, which takes the following parameters: 
- A`MemorySegment`: the address of the native function, usually obtained via `SymbolLookup`
- A `FunctionDescriptor`: a descriptor defining the signature of the target foreign function (its parameter and return types)
- Zero or more `Linker.Option`: optional settings for this linkage request

In our case we want to call the `strlen` function so we call it with `stdLibLookup.find("strlen").orElseThrow()` which returns a `MemorySegment` pointing to the native symbol address and a function descriptor `FunctionDescriptor.of(JAVA_LONG, ADDRESS)` which represents the parameter expected by `strlen` (let's suppose that size_t maps to long).

So the last think we have to dso is call the function! To do so, we have to pass to it a String, but a normal `String str = "..."` is not enough, or better, allocating a String like this results to allocate memory but on the JVM!! But this is not what we want to do... We want that memory to be accessible from the native function, so instead we use an `Arena` object, we can retrieve it using `Arena.ofConfined()` (in this case the *try-with-resources Statement* is very useful). 

After obtaining our "Memory space" (the arena), we can now allocate memory on it, arena has a good collection of method to do so, in our case we are gonna use `arena.allocateFrom("Hello, Panama!");` that allocate a **MemorySegment** from a String as the javaDoc says: 

```javadoc
/**
 * Converts a Java string into a null-terminated C string using the UTF-8 charset,
 * storing the result into a memory segment.
 *
 * @param str the Java string to convert
 * @return a memory segment containing the UTF-8 encoded null-terminated string
 */
public java.lang.foreign.MemorySegment allocateFrom(String str)
```
Finally we can call our function `long length = (long) strlen.invokeExact(cString);`, we are using `invokeExact` because it requires exact signature matching, also remember that the call to `invokeExact` or `invoke` is not direct. They're intrinsics; the virtual machine replaces them with optimized code.
> Intrinsic is a method that the JVM treats in a special way and replaces with highly optimized native code or machine instructions at runtime.

If we now print the result, we will get `"The length of the C string is: 14"` as expected.
